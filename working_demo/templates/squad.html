Bear-state machine (shared across all 4 bots)

The mascot's face is a downstream readout of the BSI engine's internal state, not a separate model. Every bot transitions through the same six states; only the threshold crossings differ.

SLEEPING
|z| < 0.5 · benign
CONFUSED
pillars disagree
THINKING
|z| 0.5 – 1.5 · drift
WORRIED
|z| 1.5 – 2.0 · watch
ANGRY
|z| 2.0 – 2.5 · fire
FIRED-UP
|z| ≥ 2.5 · scale
BLITZ fires from WORRIED onward · SCOUT from ANGRY · GUARDIAN only from FIRED-UP · ROBO evaluates the state plus the feature vector before routing.

Head-to-head: when do the bots disagree?

Edge cases pulled from the canonical 5-event backtest.

SCOUT vs BLITZ
KLAR-pulse-2024: BLITZ fired on day −18 (z=1.7, only 2 pillars). SCOUT held — required SCP confirmation, which arrived on day −9. SCOUT entered later, deeper, exited cleaner. SCOUT wins on PnL · BLITZ wins on time-to-signal
BNPL-pulse-2024: BLITZ fired three times, SCOUT once. Two of BLITZ's fires were the same event re-firing inside the cooldown gap.
GUARDIAN vs SCOUT
AFRM-2022: SCOUT fired (z=2.1), GUARDIAN abstained (FDS gate failed — 8-K disclosure was late). The miss cost GUARDIAN −12% vs SCOUT, but GUARDIAN's mandate explicitly accepts that miss.
CVNA-2022: Both fired. GUARDIAN's smaller size meant lower absolute return but a Sharpe nearly identical to SCOUT.
ROBO vs SCOUT
AFRM-2025-spread: SCOUT abstained — MOVE was elevated and the gate filter blocked. ROBO routed to its GUARDIAN-subroutine (low size, long hold), caught the spread widening, captured +14%. The routing log shows the macro-regime feature flipped the choice.
Edge: ROBO's auditability is what makes this acceptable to LPs — the routing decision is logged with the feature vector, not produced by a black-box.
BLITZ vs GUARDIAN
The widest behavioural gap in the squad. BLITZ fires ~10× more often, sizes ~6× larger, and accepts a ~22× higher FP rate. The two bots are designed to coexist — a desk could plausibly run BLITZ as a watchlist and GUARDIAN as the execution layer, only acting on the intersection. That intersection caught 1/5 events with zero false positives in the backtest.

ROBO-BEAR · routing logic in detail

The routing function is a deterministic decision tree over five features; every choice is logged next to the feature vector. There is no neural network in this layer. 

def route_robo(event, features) -> SubroutineChoice:
    """
    features = {
      "vol_z":          MOVE z-score over 60d,
      "pillar_concord": fraction of alt-data pillars agreeing,
      "macro_tail":     STLFSI4 / NFCI z-score,
      "scp_clean":      bool — SCP gate passed cleanly,
      "firm_known":     bool — name in BNPL universe (with EDGAR data),
    }
    """
    if not features["firm_known"]:
        return STAND_DOWN("unknown firm — no EDGAR / BSI history")

    if features["pillar_concord"] < 0.40:
        return STAND_DOWN("pillars disagree — concord < 40%")

    # High vol + strong concordance → strike fast
    if features["vol_z"] > 1.5 and features["pillar_concord"] >= 0.80:
        return BLITZ_SUBROUTINE(size_pct=10, stop_pct=10)

    # Macro tail risk on → stay defensive
    if features["macro_tail"] > 1.5:
        return GUARDIAN_SUBROUTINE(size_pct=3, stop_pct=5)

    # Default — published methodology
    if features["scp_clean"]:
        return SCOUT_SUBROUTINE(size_pct=5, stop_pct=7)

    return STAND_DOWN("SCP gate dirty — no clean entry")
Every STAND_DOWN, every routing choice, and every feature vector is appended to the ROBO routing log (data/apollo.db :: robo_routes). LPs who want to audit a single decision can replay the exact feature vector that produced it.
